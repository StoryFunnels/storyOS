# Design-system audit — the baseline

**Measured 2026-09-08 against `origin/main` at `67baef1`.** Ticket #623, step 1 of
four. No code changed in this ticket by design: the proposal is step 2 and the
refactor is step 3.

Every number here is reproducible:

```sh
bash docs/design/measure-baseline.sh
```

That script is the deliverable as much as this prose is. The success criteria for
this role are "the count of arbitrary `[Npx]` values goes DOWN, measurably, week
over week" and "the shared primitive count goes UP" — neither is checkable unless
anyone can re-run the count and get the same figure. Numbers that came from a
live browser instead of a grep are labelled as such.

---

## The headline: the thesis was right about colour, wrong about spacing

The hypothesis handed to me was *"colour is systematised, typography and spacing
are not."* Two thirds of that survives measurement.

| | verdict | evidence |
|---|---|---|
| Colour | **systematised** — confirmed | 45 semantic tokens, 3 dead, 5 raw colour literals in 154 files |
| Typography | **not systematised** — confirmed, and worse than reported | 1,272 arbitrary sizes across 10 distinct values; two competing scales |
| Spacing | **already systematised** — thesis WRONG | 20 arbitrary spacing values in the whole app, against 2,401 padding/gap uses of Tailwind's 4px scale (3,014 counting margins) |
| Elevation | not in the hypothesis; **not systematised** | 14 hand-rolled shadows, 0 tokens, none dark-mode aware |

**Spacing does not need a scale. It has one.** Padding, margin and gap resolve to
Tailwind's default 4px step at all but 20 call sites in `apps/web/src`:

```
18 py-[3px]      1 pt-[15vh]      1 mt-[3px]
```

against `gap-2` ×279, `px-2` ×265, `gap-1.5` ×248, `gap-1` ×186, `py-0.5` ×112 —
a long, ordinary, well-behaved distribution. Writing a spacing scale would mean
re-notating a system that already works and producing a diff that touches every
screen to change nothing. I am not going to propose that.

I will say plainly what this costs: **the charter's step 2 asks for "a type scale
AND a spacing scale", and I intend to deliver only the type scale**, plus the
elevation scale the audit turned up instead. If Otto wants the spacing work
anyway, the argument against is in this section and I would like it answered
rather than overridden silently.

One caveat, because it is the one thing that IS wrong with spacing: the
design-system doc says "8px grid" and the code is on a 4px grid with heavy use of
2px and 6px steps (`py-0.5`, `gap-1.5`). The doc is wrong, not the code. That is a
documentation fix, not a refactor.

## 1. Every distinct arbitrary size, with call-site counts

### 1a. The debt is almost entirely font-size

1,928 bracket-notation utilities in `apps/web/src`. That headline number is
misleading and I nearly reported it as the debt, so it is worth splitting:

```
bracket utilities total   1,928
  reference a token         513   ← rounded-[var(--radius-control)] etc. This is
                                    GOOD discipline in awkward syntax, not debt
  arbitrary literal       1,415
```

Of those 1,415 literals, **1,272 (90%) are `text-[Npx]`**:

| value | occurrences | | value | occurrences |
|---|---|---|---|---|
| `text-[13px]` | **548** | | `text-[14px]` | 15 |
| `text-[12px]` | **411** | | `text-[9px]` | 5 |
| `text-[11px]` | **250** | | `text-[15px]` | 5 |
| `text-[10px]` | 33 | | `text-[8px]` | 2 |
| | | | `text-[16px]` | 2 |
| | | | `text-[22px]` | 1 |

Ten distinct sizes; 111 of 125 files that set any size use `text-[13px]`.

**The hypothesis numbers (432 / 323 / 182) are stale, and the trend is the
finding.** Same query on older commits:

| commit | date | `text-[13px]` |
|---|---|---|
| `31632f9` | 2026-08-19 | 474 |
| `90493ee` | 2026-09-01 | 515 |
| `67baef1` | 2026-09-08 | **548** |

That is **+74 in twenty days, ~+25/week, and accelerating**. The debt is not
static; it is being added to faster than any migration I could run one surface at
a time. This is the strongest argument for doing step 2 and step 3 promptly:
every week of delay is another ~25 call sites to convert.

### 1b. Everything else is small and mostly legitimate

The other 143 arbitrary literals, by category:

- **Dimensions — 61 occurrences, 35 distinct.** Mostly justified one-offs:
  `max-h-[75vh]` ×8, `max-w-[calc(100vw-2rem)]`, viewport-relative modal caps.
  *Not* a systematisation target — with one exception: `min-h-[44px]` ×5,
  `min-h-[48px]` ×4, `min-h-[56px]` ×3, `min-h-[36px]` ×2 are touch-target and
  row-height constants written as literals in four different places. Those want
  tokens.
- **Radius — 8 literal occurrences** (`rounded-[3px]` ×4, `[6px]` ×2, `[8px]`,
  `[2px]`) against 385 tokenised. Two of the literals restate the token's own
  value: `rounded-[6px]` **is** `--radius-control`.
- **Shadow — 30 occurrences, 14 distinct.** See §4.
- **Colour — 5 literal occurrences** in 154 files: `bg-[rgba(15,23,41,0.35)]` ×5
  and `bg-[#FAF7F1]` ×3 (which restates `--bg-app`). Colour discipline is real.
- **Line-height — 1 arbitrary value in the entire app** (`tracking-[0.03em]`).
  Which brings us to the defect that matters most.

### 1c. The real typographic defect: there are TWO type scales and they disagree

This is the finding I would most like read carefully, because it changes what
step 2 can safely do.

Two scales are in use side by side:

```
arbitrary px      1,272 uses     text-[13px], text-[12px], …
Tailwind named      174 uses     text-sm ×125, text-lg ×36, text-xl ×7, text-2xl ×3, …
```

They do not line up. Measured in Chrome on the running app:

| written | computed size | computed line-height | ratio |
|---|---|---|---|
| `text-[13px]` | 13px | 19.5px | 1.50 |
| `text-sm` | **14px** | **20px** | 1.43 |
| `text-[14px]` | 14px | 21px | 1.50 |

Three separate problems in that table:

1. **`text-sm` is 14px, but the app's de-facto body size is 13px** (548 sites vs
   125). A builder who reaches for the obvious named utility gets a control one
   pixel larger than the control beside it.
2. **At the *same* 14px, the two notations produce different leading** — 20px via
   `text-sm`, 21px via `text-[14px]`. So the systems differ in leading as well as
   size, and a file that mixes them gets inconsistent rhythm at identical size.
3. **53 files already contain both `text-sm` and `text-[13px]`.** The split is not
   between old and new code; it is inside individual files.

The primitive library itself carries the contradiction. `ui/button.tsx` base
class is `text-sm` (14px), and its own `size="sm"` variant overrides to
`text-[13px]`. `ui/input.tsx` is `text-sm`; `ui/label.tsx` is `text-[13px]`. So on
the **first screen a new user ever sees**, measured live, the label reads 13px and
the input it labels reads 14px:

```
label   "Email"    13px / 19.5px / w500
input   (email)    14px / 20px   / w400
```

And line-height is not a typographic decision anywhere: `text-[Npx]` sets
font-size only, so all 1,272 sites inherit leading from an ancestor. The whole app
has **25 explicit `leading-*` declarations**.

### ⚠ This is why step 3 cannot be done as written, and I need a decision

My charter says: *"define them to match the values already in use — `text-sm` IS
13px, because 13px is what 432 call sites already say."*

Followed literally, that redefines Tailwind's `text-sm` from 14px to 13px — and
**silently shrinks the 125 call sites that already use `text-sm` meaning 14px**,
including every `<Button>` and every `<Input>` in the product. That is a
fifty-screen visual change arriving through the back door of a "pure refactor",
which is the one thing the charter forbids absolutely.

The two instructions cannot both be satisfied. Per the house rule on
contradictory instructions I am naming both rather than picking, and the decision
goes on the step-2 ticket for Otto. My recommendation, with reasoning, is there.
I am **not** blocked meanwhile — the audit, the baseline script and the defect
tickets do not depend on the answer.

## 3. Colour tokens: 66 names, 45 semantic, 3 dead

The hypothesis said 71 custom properties. The real structure:

```
45  semantic tokens in :root          (colour, radius, z-index)
25  @theme inline aliases             (--color-*, --font-sans, --radius-*)
66  unique property names in the file (the two sets overlap on the radius names)
```

31 of the 45 semantic tokens are redeclared under `:root[data-theme='dark']`
(the colour ones; radius and z-index do not change with theme).

**Three tokens are dead:** `--accent-hover`, `--z-sticky`, `--z-toast`. Full
liveness table: `python3 docs/design/token-liveness.py`.

A methodology note that is itself a finding. My first pass reported **32** dead
tokens. That was wrong, and wrong in an instructive way: the colour tokens are
consumed neither by their own name nor by their alias name, but by *generated
Tailwind utility classes* (`--bg-card` → `--color-card` → `bg-card` ×326). A
name-only grep declares the entire working colour system dead. Any future "unused
token" cleanup that greps for names will delete live tokens.

The three dead ones are each worth a sentence:

- **`--accent-hover`** — declared in both themes, forwarded to
  `--color-accent-hover`, and the generated utility has **0 call sites**. Hover
  states use `--accent-hover`'s sibling or a bespoke value instead.
- **`--z-sticky: 10` and `--z-toast: 100`** — not really dead, *unadopted*. Both
  are asserted by `z-scale.unit.test.ts`, so their ordering is enforced, yet no
  call site uses either. `--z-sticky` is commented "sticky table headers, in-flow
  toolbars" and the sticky table headers use raw `z-10`. There are **33 raw
  z-index utilities** (`z-10` ×13, `z-20` ×9, `z-40` ×7, `z-30` ×3, `z-0`) — legal,
  because the #422 sweep only catches `fixed inset-0 … z-N`, but unsystematised.
  Six raw `z-40`s sit exactly on `--z-overlay-backdrop`'s layer.

### Where colour discipline actually leaks

Not in components — in `globals.css` itself:

```css
*:focus-visible { box-shadow: 0 0 0 3px rgba(212, 160, 23, 0.25); }
```

That is `--accent`'s light-mode value, hardcoded. Dark mode lifts `--accent` to
`#e0af2b`, so **the focus ring is the only element in the app that does not follow
the theme.** The design-system doc even specifies a `--focus-ring` token for this;
it was never added (0 occurrences in `globals.css`).

## 4. Elevation: not in the hypothesis, and the clearest quick win

There is no `--shadow-*` token. There are 14 distinct hand-rolled shadows across
30 call sites, all on the same `rgba(15,23,41,α)` ink:

```
 5×  0 8px 24px  …0.25      3×  0 4px 12px …0.12      1×  0 24px 60px …0.28
 5×  0 4px 12px  …0.08      2×  2px 0 4px -2px …0.12   1×  0 20px 50px …0.2
 3×  0 8px 24px  …0.15      2×  0 16px 40px …0.22      1×  0 20px 50px …0.15
 3×  0 4px 12px  …0.15      1×  0 8px 24px …0.18       1×  -8px 0 24px …0.08
                            1×  0 4px 12px …0.1        1×  inset 2px 0 0 var(--accent)
```

Read the offsets: this is a real elevation scale — 4/12, 8/24, 16/40, 20/50,
24/60 — that someone re-derived from memory each time, landing on **four different
opacities for the same 4px/12px popover shadow** (0.08 ×5, 0.1 ×1, 0.12 ×3,
0.15 ×3 — twelve sites, four values). The doc specifies exactly two shadows; the
code has 14.

> **Corrected 2026-09-08.** The first version of this paragraph said *six*
> different opacities while listing four, and the wrong number reached PR #660's
> description and ticket #624, where it was quoted back to me inside the D3
> approval. It is four. The conclusion is unchanged — 14 distinct values, no
> token, one geometry carrying four opacities across twelve call sites — but the
> figure was wrong and a decision was taken partly on it, so it is corrected
> here rather than quietly edited.

Two consequences:

1. **None of them adapt to dark mode.** They are literal `rgba`, not `var()`. A
   near-black shadow on a `#171c26` card does nothing — so in dark mode floating
   surfaces lose their separation from the page, which is the entire job of the
   shadow. (Measured only in the CSS; I did not verify the visual severity in dark
   mode in the browser — see Gaps.)
2. Five tokens (`--shadow-popover`, `--shadow-modal`, `--shadow-drawer`, plus dark
   overrides) would retire all 30 sites, and unlike the type scale this one has
   **no ambiguity about the target values** and no competing scale to reconcile.

I would rather land this before the type scale. It is smaller, it is a genuine
dark-mode correctness fix rather than a tidy-up, and it makes step 3's
zero-visual-change claim easy to prove on a small diff first.

## 5. The five screens a new user hits first

Walked in a real browser at `localhost:3070` against a fresh account and a
fresh `storyos_dara` database, in this order. Every figure below is a computed
style read out of the live page, not inferred from source.

### Screen 1 — `/signup`, "Create your account"

**Named defect: a form field and its own label are different sizes.**

```
label "Email"     13px / 19.5px / w500     (ui/label.tsx  → text-[13px])
input  email      14px / 20px   / w400     (ui/input.tsx  → text-sm)
button "Sign in"  14px / 20px   / w500     (ui/button.tsx → text-sm)
```

Not a taste call — two primitives that are always used together disagree, so
every form in the product inherits the mismatch. Fixing it in the two primitives
fixes it everywhere, which is what makes it mine rather than Iris's.

### Screen 2 — `/new-workspace`, "Create your workspace" + Business Pack picker

**Named defect: 10px body text, and six type styles in one viewport.**

```
10px / 15px / w400   ×24 leaves   "databases", "1 automation", "1 agent"
12px / 18px / w400   ×11          pack descriptions
13px / 19.5px / w500 ×12          "Workspace name"
16px / 24px / w600   ×8           the database COUNT ("4")
18px / 28px / w600   ×1           "Create your workspace"
14px / 20px / w500   ×1           the CTA
```

The 10px labels are the words that explain what a Business Pack contains — the
single most load-bearing text on the screen that decides which pack a new user
installs — and they are the smallest type in the product. Contrast is fine
(≈5.7:1, `--text-muted` on white); **this is a size problem, not a contrast
problem**, and I checked rather than assuming: the lowest contrast I could measure
anywhere on this screen was 5.73:1, comfortably over AA.

Also: the pack card nests **three levels of bordered box** (card → count tile →
two chips), measured by walking computed `border-top-width` down the tree.

### Screen 3 — the table view (landed on automatically after pack install)

The screen users live in all day. **Named defect: 13 distinct type styles and 22
distinct interactive control shapes in a single viewport.**

Font sizes present: **10, 11, 12, 13, 14, 16px** — six sizes.
Radii present: **0px, 4px, 6px**.

Control shapes (height × font-size × radius), most frequent first:

```
18×  h=26 fs=13px r=4px     sidebar nav rows
11×  h=20 fs=13px r=0px     space children
10×  h=18 fs=14px r=4px
10×  h=18 fs=12px r=4px
 9×  h=32 fs=12px r=0px     column headers
 3×  h=26 fs=12px r=4px     Filter / Sort / Hide fields
 1×  h=24 fs=14px r=6px     ← the ONLY 6px control on the screen
…22 shapes in total
```

That last line is the finding. **`--radius-control` is 6px, is used at 230 call
sites, and exactly one of the 22 control shapes on the primary screen renders at
6px.** Everything else is 4px — Tailwind's bare `rounded`, used 275 times, more
often than the token itself. The documented "controls/inputs/cells 6px" is not
what the main screen shows, and a builder copying a neighbouring control copies
4px.

The sidebar row and the toolbar button are both 26px tall with *different* text
sizes (13px vs 12px).

### Screen 4 — `/w/{ws}`, Home

**15 distinct type styles, 13 control shapes, 3 radii** (8px ×19, 4px ×2, pill ×2).

The finding here is the shape of the split: this screen's heading is
`20px / 28px / w600` — `text-xl`, from Tailwind's named scale — while every piece
of body and UI text around it is arbitrary px. **Headings are on the named scale;
body and UI text are on arbitrary px. The two systems never meet, and neither is
documented.**

### Screen 5 — the record split-screen (row → Open)

**Named defect: the record title is clipped mid-word with no ellipsis, at a
standard laptop width.**

Measured on the editable title `<input class="… text-2xl font-semibold …">` with
the value `Acme Co (sample)` — 16 characters:

| viewport | field width | content needs | result |
|---|---|---|---|
| 1440 × 900 | **168px** | 202px | **clipped by 34px** → renders "Acme Co (samp" |
| 1512 × 945 | 204px | 204px | just fits |
| 1920 × 1080 | 408px | 408px | fits |

`text-overflow: clip`, not `ellipsis` — so there is no visual signal that the name
is truncated at all. A 24px display size sits in a column with no reserved
minimum width; at 1440px, an extremely common laptop width, a sixteen-character
client name is unreadable. Any longer name clips at 1512 too.

**Second defect, same surface, narrower viewports.** At 1131px (above the mobile
breakpoint, so the desktop three-column layout is still in force) the middle
column collapses and text wraps to roughly one word per line:

```
"Nothing linked yet."            13px in a  44px-wide box, 79px tall  (~5 lines)
"Drop files here or use Upload."  12px in a  41px-wide box, 90px tall
```

Both are feature-screen defects in surfaces I do not own — I am filing them with
these measurements and routing them, not fixing them.

## What I did NOT check

- **Dark mode was not walked in the browser.** Every dark-mode claim here is read
  from `globals.css`, not seen. The shadow claim in §4 in particular ("floating
  surfaces lose separation") is a reasoned consequence of literal `rgba` shadows,
  **not a reproduction**. It needs a click-through before anyone treats it as
  confirmed.
- **Only the five first-run screens were measured live.** Board, calendar,
  timeline, gallery, form, dashboard and every settings page are counted in the
  static greps but were not opened. `view-toolbar.tsx` (56 arbitrary sizes) and
  `admin/page.tsx` (60) are the two densest files in the app and I have not
  looked at either on screen.
- **No accessibility audit.** I measured contrast on two screens only, and checked
  no focus order, no keyboard traps, no screen-reader behaviour.
- **`<button>`'s 331 raw uses were not individually classified.** I sampled them;
  I did not determine how many *should* be `<Button>`. The 61% bypass rate is a
  real count but not a to-do list.
- **The 1131px column collapse has no identified cause.** I measured the symptom
  and did not trace which container lacks the `min-width`.
- **Mobile and tablet widths were not tested at all.**
- **Every prose figure has now been re-checked against the script** (2026-09-08,
  after the "six opacities" error below). Two more were imprecise and are fixed
  above: the tokenised-radius total was 382 and is **385** — my sum omitted the
  three directional variants (`rounded-r-`, `rounded-l-`, `rounded-br-`) — and
  "~2,400 spacing uses" is **2,401** padding/gap uses, or 3,014 counting margins,
  so the figure is right only as scoped and now says which. Everything else
  matched exactly: 1,272 arbitrary sizes, 548/411/250, 14 shadows over 30 sites,
  33 raw z-indexes, 125 `text-sm`, 114 raw `<select>`, 66 tokens / 45 semantic /
  3 dead. The lesson worth keeping: the table figures came from
  `measure-baseline.sh` and were all correct; the three that were wrong were all
  hand-written prose. Derive the sentence from the script, not from memory.
- **`rounded-control` does not work, and I nearly claimed it did.** I expected
  Tailwind v4 to generate a `rounded-control` utility from
  `@theme inline { --radius-control: 6px }`, which would have meant 385 call sites
  were verbose out of ignorance. Probed in the live page:
  `rounded-control` computes to `border-radius: 0px`. The utility is not
  generated, so `rounded-[var(--radius-control)]` is the only thing that works and
  those call sites are correct. Recorded because the wrong version of this
  paragraph would have sent someone on a 385-site refactor that breaks every
  radius in the app.

## One process note, reported against myself

Setting up a dev instance, I ran `pnpm --filter @storyos/api db:migrate` before
creating my own database. `drizzle.config.ts` falls back to
`postgres://storyos:storyos@localhost:5432/storyos` when `DATABASE_URL` is unset,
and the API's own `load-env.ts` reads `apps/api/.env` — which did not exist yet —
so the command ran against the **shared `storyos` dev database**, not mine.

It was a no-op: 91 migrations on disk, 91 already applied there, newest stamped
`2026-09-08 00:14`, hours before my run. Nothing changed. But the guard rail that
saved it was luck, and `load-env.ts`'s own header comment documents this exact
hazard ("pointing a UAT run at an isolated database and watching the API keep
